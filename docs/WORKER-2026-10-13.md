# Render worker qualification — 12–13 October 2026

The shared `GPUSceneEngine` now owns WebGPU, flow, the volume-generation worker and all frame measurement. The DOM controller runs either the same engine on the main thread (default / `?worker=0`) or on a dedicated render worker (`?worker=1`) with a transferred OffscreenCanvas. Shader, volume generation, morphology, lighting and animation are unchanged: 256³ density, 128³ detail, 384 nominal steps, no TAA or adaptive resolution. One transfer/start promise per controller; worker shutdown waits for core cleanup with a one-second termination fallback. Terminal failures disable controls and discard subsequent output. Unsupported worker startup reports an error rather than changing quality.

**Stable 60 remains an open gate.** Continuous Full-HD growth reached 59.99 fps over 90 seconds with no intervals over 18 ms. Window/right/orbit reached 59.97 with one 34 ms interval. But the first left/right worker runs fell to 57.46/57.19, capped right to 50.95, and repeated continuous right was 59.83 with seven intervals over 33.34 ms and p95 20.6 ms. The candidate is retained as opt-in, not promoted as a proven performance fix. The ordinary main-thread renderer remains the default.

The 30-second main/worker A/B control reached 59.992/59.993 fps, both with no intervals over 18 ms. It does not isolate a worker benefit. Different runs have different cloud phases and host conditions; even the same-context policy switches are sequential, not causal proof. Queue completion rose to 49–64 ms while GPU render remained about 5.6 ms. A later growth run had 7.34 ms completion. Moving submission to a worker reduces exposure to document-thread work but does not bypass GPU scheduling, IPC, compositor or host pressure. No exclusive source of the long waits has been established.

The owner confirms backups paused. Service activity does not establish uploads; no unrelated process was stopped. Direct compositor presentation timestamps are unavailable through the current browser tooling. All FPS values are visible worker/main RAF submission cadence, not proof of frames presented to the monitor. `onSubmittedWorkDone()` includes work ahead of the fence and asynchronous delivery, not presentation. [GPUQueue API](https://gpuweb.github.io/types/interfaces/GPUQueue.html#onSubmittedWorkDone). Inspected Chromium queue source flushes submission immediately; calling a completion fence is not evidence that an otherwise unflushed submit was repaired. [Chromium GPUQueue implementation](https://chromium.googlesource.com/chromium/src/third_party/%2B/ec509b190c91fe85dc247e85b6dfe91f30d5da2a/blink/renderer/modules/webgpu/gpu_queue.cc). The installed Three r186 backend submits compute and render separately; naïvely combining them would need to preserve intervening buffer/texture-write order and is not implemented speculatively.

Worker RAF/local clocks were checked without an offset correction. First callback deltas were 7/13 ms during initialization; measured dispatch was finite and nonnegative, typically 0.17–1.91 ms depending on the run. The exported clock sample records RAF timestamp, local time and local time origin. GPU timestamp increments remain 0.065536 ms; tiny compute averages do not imply finer precision.

One visible in-app browser renderer, seed 1571198069, AMD GCN-5 hardware (not fallback), Chromium155, Three186, production preview4177. Every 30/90-second interval capture includes a two-second warmup, excludes that warmup from statistics and keeps the panel closed. No builds/tests/screenshots during the captures. Fixed Full-HD means 1920×1080 actual/internal; window means 1143×954, one pixel per CSS pixel, not DPR2.2 native rendering. Capped skip totals include warmup.
